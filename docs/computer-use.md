# Browser use & computer use

Ion gives the agent two levels of "hands": a sandboxed embedded
browser it can drive inside the app, and (opt-in) real control of your Mac's
mouse, keyboard, and screen. Both are visible - you watch the cursor move.

## Browser use (embedded panel)

**On by default** (Settings → Agent abilities → *Browser use*). Safe: the agent
only ever touches a `<webview>` guest inside the app window, never your real
browser or OS.

- The panel lives on the right side of the chat view (globe button in the
  header, or it auto-opens when the agent starts browsing).
- A gold cursor overlay glides to each target and pulses on click, driven by
  IPC events from the main process, so every agent action is watchable.
- You get a URL bar and back button too - it's a real browser panel.

### Tools (never approval-gated)

| Tool | What it does |
|---|---|
| `browser_navigate(url)` | Load a URL (defaults to https:// when scheme omitted) |
| `browser_snapshot()` | Compact outline of interactive elements with stable refs (`e1`, `e2`, …) plus visible text |
| `browser_click(ref \| x,y)` | Trusted click via `sendInputEvent`, cursor glides there first |
| `browser_type(text, ref?)` | Type into the focused (or ref'd) element |
| `browser_press_key(key)` | Press a key or combo (`Enter`, `cmd+a`, …) |
| `browser_scroll(dy \| ref)` | Scroll by pixels or bring a ref into view |
| `browser_screenshot()` | PNG of the page - attached as image input for Grok, saved under `~/.ion/screenshots/` |
| `browser_back()` | History back |

Snapshots are generated by injected JavaScript (`role/name/ref` per element);
refs are stable until the next snapshot or navigation. The system prompt tells
the agent to snapshot before clicking and re-snapshot after page changes.

Implementation note: the panel is an Electron `<webview>` tag (chosen over
`WebContentsView` because it participates in React/CSS layout directly - no
manual bounds syncing). The main process finds the guest `WebContents` and
drives it with `loadURL`, `executeJavaScript`, `sendInputEvent`, and
`capturePage`.

## Computer use (macOS, opt-in)

**Off by default.** Enable in Settings → Agent abilities → *Computer use*.
Every single action is **approval-gated** in chat (unless you turn on
the Full access permission mode, which is not recommended together with
computer use).

### Tools (all `dangerous`, all approval-gated)

| Tool | What it does |
|---|---|
| `computer_screenshot()` | Full-screen capture via `/usr/sbin/screencapture`, attached as image input |
| `computer_move_mouse(x, y)` | Glides the real cursor in ~24 interpolated steps (~300 ms) - never teleports |
| `computer_click(x, y, button?, double?)` | Moves smoothly, then clicks; a gold ring flashes at the click point |
| `computer_type(text)` | Types via System Events keystrokes |
| `computer_press_key(combo)` | Key combos like `cmd+t`, `cmd+shift+s`, `enter` |
| `computer_scroll(dx, dy)` | Scroll wheel events at the current pointer |

### Implementation: no native modules, no external binaries

Everything rides on tools already present on macOS:

- **Screenshots** - `/usr/sbin/screencapture -x`.
- **Mouse + scroll** - `osascript -l JavaScript` (JXA) calling CoreGraphics
  (`CGEventCreateMouseEvent` / `CGEventCreateScrollWheelEvent` / `CGEventPost`).
  Cursor interpolation runs inside a single JXA process so movement is smooth.
- **Keyboard** - AppleScript System Events (`keystroke` / `key code` with
  modifier lists).
- **Click highlight** - a transparent, frameless, click-through, always-on-top
  Electron window flashes a pulsing ring at the click point.

Nothing to `npm rebuild`, nothing to `brew install`.

### macOS permissions

Grant these to the app you launch Ion from (in dev that's Electron /
your terminal app; in a packaged build it would be Ion itself):

| Permission | Needed by | Where |
|---|---|---|
| **Screen Recording** | `computer_screenshot` | System Settings → Privacy & Security → Screen Recording |
| **Accessibility** | mouse, keyboard, scroll | System Settings → Privacy & Security → Accessibility |

The app detects missing permissions (via `systemPreferences`) and the tools
return actionable error messages pointing at the right pane instead of failing
silently. macOS usually shows its own grant prompt on first use; restart the
app after granting.

### Safety model

- Off by default; enabling it is an explicit Settings action.
- Every tool call is `dangerous: true` → in-chat approval with the exact
  arguments shown (coordinates, text, key combo) before anything happens.
- Cursor movement is deliberately slowed and visible so you can track it -
  and you can deny the next action at any approval prompt.
- Screenshots are saved under `~/.ion/screenshots/` and sent to the
  model as transient image input; base64 payloads are never written into the
  session transcript on disk.

## Vision plumbing (how screenshots reach Grok)

Tool results can carry images (`{ mimeType, base64 }`). The xAI client expands
an image-bearing tool result into the Responses API as the usual
`function_call_output` plus a follow-up `user` message containing
`input_image` content parts with base64 data URIs (`detail: "high"`) - the
pattern xAI documents for image input; grok-4 models are vision-capable.

To keep requests and disk lean:

- only the **2 newest** screenshots stay in model input (older ones are
  stripped automatically);
- the session store strips `images` on persist, so transcripts stay small.

## Grok tuning (system-wide)

- `temperature: 0.2` and `parallel_tool_calls: true` on every request;
  `reasoning: { effort: "medium" }` on models that support it (grok-4.5/4.6
  families). All configurable via `XaiClientConfig`.
- Retries with exponential backoff + jitter on 429/408/5xx, honoring
  `Retry-After`; aborts are never retried.
- A ~200k-token context budget in the agent loop drops the oldest
  conversation items (never the system prompt or current turn) so long
  sessions keep working - and stay under xAI's long-context billing tier.
- The system prompt is tuned for agentic Grok behavior, with dedicated
  browser-use / computer-use sections that appear only when those tools are
  actually offered.
